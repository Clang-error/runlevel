# runlevel 은 어떻게 돌아가는가

설정창의 "작동 방식" 섹션에 넣을 후보 원고.
섹션마다 독립적으로 읽히게 썼으니, 사용자에게 보여줄 것만 골라 쓰면 된다.

---

## 1. 한 줄 요약

**리눅스가 당신의 브라우저 안에서 진짜로 돌아간다.** 서버에 접속하는 게 아니다.

`ls` 를 치면 진짜 `ls` 바이너리가 진짜 리눅스 커널 위에서 실행된다.
흉내 낸 셸이 아니고, 미리 준비된 출력을 보여주는 것도 아니다.

---

## 2. 전체 그림

```
┌─ 브라우저 탭 ────────────────────────────────────────────┐
│                                                          │
│   ┌─ v86 (WebAssembly x86 에뮬레이터) ─────────────┐      │
│   │                                                │      │
│   │   Linux 6.18 커널  +  Alpine Linux 유저랜드     │      │
│   │                                                │      │
│   │   ttyS0 ─── 당신이 보는 터미널                   │      │
│   │   ttyS1 ─── 채점기 (화면에 안 보임)              │      │
│   └────────────────────────────────────────────────┘      │
│                     ↑                                     │
│              xterm.js 터미널 UI                            │
└──────────────────────────────────────────────────────────┘

바깥으로 나가는 연결: 없음
```

서버는 정적 파일(HTML, JS, 디스크 이미지)만 내려준다.
**명령이 실행되는 곳은 당신의 브라우저다.** 게스트에서 바깥으로 나가는 길은 없다.

한 가지 예외는 문제를 마칠 때 보내는 기록인데, 그건 게스트가 아니라 앱이 보내는
것이고 문제를 고치는 데만 쓴다 (13-1 참고). 설정에서 끌 수 있다.

---

## 3. 브라우저가 어떻게 x86 CPU를 돌리나

**v86** 이라는 오픈소스 에뮬레이터를 쓴다. x86 CPU, 메모리, IDE 디스크 컨트롤러,
시리얼 포트, VGA 카드를 WebAssembly 로 구현한 것이다.

- 게스트가 실행하는 기계어를 v86 이 한 명령씩 해석하거나 WASM 으로 번역해 실행한다
- 그래서 **속도는 실제 CPU 보다 훨씬 느리다.** 대신 커널을 그대로 올릴 수 있다
- 특별한 브라우저 설정(COOP/COEP 헤더 등)이 필요 없다. 정적 호스팅이면 어디서든 뜬다

`SharedArrayBuffer` 를 요구하는 다른 방식(CheerpX, Wasmer 등)과 달리
이 점 때문에 v86 을 골랐다. 그리고 그 방식들은 커널이 없어서
`mount` 나 `fdisk` 같은 걸 아예 못 한다.

---

## 4. 시작 과정 — 부팅하지 않는다

페이지를 열면 **홈(문제 목록)이 먼저 뜨고**, 그 뒤에서 **부팅이 끝난 상태를 그대로
복원한다.** 약 **2초**. 목록을 훑는 동안 복원이 끝나 있어서, 문제를 고르면 바로 열린다.
아직 안 끝났으면 고른 문제를 붙잡아 뒀다가 준비되는 대로 연다.

미리 부팅해 둔 컴퓨터의 메모리와 디스크 상태를 통째로 저장해 두고,
접속하면 그 시점으로 되돌린다. 실제로 부팅하는 과정은 없다.

이렇게 한 이유는 **부팅이 CPU 성능을 그대로 타기 때문**이다.
CPU 를 느리게 만들어 측정해 보니 이렇게 벌어졌다.

| CPU | 부팅했을 때 | 복원했을 때 |
|---|---|---|
| 기준 | 7.0초 | 1.8초 |
| 2배 느림 | 16.7초 | 1.9초 |
| 4배 느림 | 44.8초 | 2.2초 |
| 6배 느림 | 55.3초 | 2.5초 |

복원은 압축을 풀어 메모리에 옮기는 일이라 기기 성능을 거의 타지 않는다.

### 참고 — 실제 부팅은 이렇게 진행된다

`?boot=1` 을 붙이면 복원 대신 진짜로 부팅한다. 약 8초.

| 시각 | 무슨 일이 일어나는가 |
|---|---|
| 0.0s | SeaBIOS 가 초기화 |
| 0.7s | 커널이 initramfs 압축 해제 |
| 1.8s | `/init` 실행 |
| 2.5s | ATA 드라이버 로드, 디스크 인식 |
| 5.7s | ext4 루트 파일시스템 마운트 |
| 6.0s | 셸 프롬프트 |

부팅 화면은 기본적으로 감춰져 있다. `?selftest=1` 을 붙이면 BIOS 부터
커널 로그까지 실제 부팅 과정을 볼 수 있다.

## 5. 무엇을 받는가 — 26.8MB

| 파일 | 크기 | 정체 |
|---|---|---|
| 스냅샷 | 23.6MB | 부팅이 끝난 상태 전체 (메모리 + 디스크 내용) |
| v86 엔진 | 2.0MB | WebAssembly |
| UI | 1.1MB | xterm.js 등 |

한 번 받으면 브라우저가 캐시한다. 두 번째 방문부터는 재다운로드가 없다.

스냅샷에 디스크 내용이 들어 있어서 **커널·initramfs·디스크 이미지를 따로 받지 않는다.**

디스크 이미지 자체는 처음에 153MB 였다. 이렇게 줄였다.
- gzip 으로 미리 압축하고 브라우저가 직접 해제 (호스트의 압축 설정에 기대지 않는다)
- initramfs 에서 안 쓰는 커널 모듈 348개 제거 (14.1 → 5.1MB)
- 빈 공간을 0으로 덮어 압축률 개선 (지운 파일의 잔재가 그대로 압축되고 있었다)
- 디스크를 실사용에 맞게 축소 (128 → 64MB)

**스냅샷을 34.2MB 에서 23.6MB 로 줄인 방법은 좀 뜻밖이었다.**

디스크만 따로 압축하면 10.4MB 인데 스냅샷 전체는 34.2MB 였다. 차액 23MB 가
메모리에 있었고, 그 정체는 **페이지 캐시** — 부팅하며 읽은 파일이 RAM 에 사본으로
남아서, 디스크와 **같은 내용이 두 번** 저장되고 있었다.

게스트 RAM 을 128 → 96MB 로 줄여봤지만 0.35MB 밖에 안 줄었다. 잘라낸 위쪽은
이미 비어 있었고 데이터는 아래쪽에 몰려 있었기 때문이다. (64MB 는 아예 못 뜬다 —
v86 이 initrd 를 물리주소 64MB 자리에 올려서, 메모리가 딱 64MB 면 놓을 자리가 없다.)

답은 **캐시를 반환시킨 뒤 그 자리를 0으로 덮는 것**이었다. 반환만 해서는 옛 바이트가
그대로 남아 압축률이 똑같다. tmpfs 에 0을 써서 덮으면 zstd 가 그 영역을 통째로 뭉갠다.
단 RAM 전체를 채우면 OOM 킬러가 셸을 죽인다 (실측: 84MB 를 채웠더니 게스트가 죽은 채로
스냅샷이 저장됐다). 지금은 128MB 중 70MB 만 채우고, 채운 뒤 게스트가 살아 있는지
확인해서 아니면 저장을 거부한다.

## 6. 채점이 화면에 안 보이는 이유 — 시리얼 두 개

게스트에 시리얼 포트를 **두 개** 붙였다.

| 포트　　　| 용도　　　　　　　 | 계정　　　　　　　　　　　　　　|
| -----------| --------------------| ---------------------------------|
| **ttyS0** | 당신이 보는 터미널 | 문제가 지정 (root 또는 student) |
| **ttyS1** | 채점 전용　　　　　| 항상 root　　　　　　　　　　　 |

채점기는 ttyS1 로 명령을 보내 결과를 확인한다. 당신 화면에는 아무것도 안 뜬다.
명령을 입력하는 도중에 채점이 돌아도 서로 간섭하지 않는다.

한 채널만 썼다면 "채점 중에는 입력을 막는다" 같은 군더더기가 필요했을 것이다.

**채점 명령을 주고받는 방식**은 이렇다.

```sh
echo "__RUN""__"; <명령>; echo "__CHK""__$?"
```

마커를 문자열로 쪼개 보내는 게 요령이다. 셸은 입력한 명령줄을 그대로 되울리기
때문에, 마커를 통째로 보내면 되울린 쪽에서 먼저 걸려 오탐이 난다.
쪼개 보내면 되울림에는 쪼개진 채로, 실행 결과에는 합쳐진 채로 나타난다.

마커에는 **일련번호**도 붙는다. 번호가 없으면 타임아웃된 명령의 마커가 뒤늦게
도착했을 때 다음 명령이 그걸 자기 결과로 읽는다 — 실제로 "풀기 전인데 목표가
통과로 뜨는" 증상으로 나타났다.

그리고 이 채널로 보내는 명령은 **한 번에 하나씩** 줄을 세운다. 채널은 하나인데
부르는 곳은 넷이다 (채점, 파일트리, 터미널 크기 조절, 계정 확인). 겹치면 한쪽
명령의 에코가 다른 쪽 출력 구간에 섞여서 둘 다 못 쓰게 된다. 게스트는 어차피
명령을 하나씩 처리하므로 병렬로 보내도 빨라지지 않는다 — 섞이기만 한다.

## 7. 채점 방식 — 명령이 아니라 결과를 본다

**정답 명령어를 비교하지 않는다.** 시스템이 원하는 상태가 되었는지만 본다.

```yaml
check:
  - desc: error.txt 가 존재한다
    cmd: test -f /work/error.txt
  - desc: ERROR 줄만 들어있다
    cmd: '[ -s /work/error.txt ] && ! grep -qv ERROR /work/error.txt'
```

각 조건은 게스트에서 실행되는 셸 명령이고 **종료 코드 0이면 통과**다.
그래서 `grep` 으로 풀든 `awk` 로 풀든 `sed` 로 풀든 결과만 맞으면 통과다.
이게 진짜 실력 측정이라고 봤다.

조건이 하나씩 쪼개져 있어서 어디까지 왔는지 보인다.
"다 맞음/틀림" 하나로 뭉치면 뭘 빠뜨렸는지 알 수 없다.

**목표(check)와 전제(guard)를 나눈다.**

- **목표** — 풀어야 달성되는 것. 아직 못 이룬 건 회색으로 조용히 있는다
- **전제** — 처음부터 참이고 끝까지 참이어야 하는 것 ("다른 파일은 건드리지 않았다").
  깨지면 빨간색으로 경고한다

빨간색은 정말 잘못했을 때만 나온다. 아직 안 한 것은 틀린 게 아니다.

**채점 시점**은 명령을 칠 때마다다. 제출 버튼이 없다.
한 줄로 푸는 사람과 여러 명령으로 나눠 푸는 사람이 둘 다 자연스럽게 커버된다.

## 8. 문제는 어떻게 정의되는가

문제 하나 = YAML 파일 하나. 코드를 건드리지 않고 파일만 추가하면 늘어난다.

```yaml
id: text-03
category: 텍스트 처리
level: 2
prompt: |
  /work/app.log 에서 ERROR 가 포함된 줄만 골라 /work/error.txt 로 저장하라.
setup:
  cwd: /work
  files:
    /work/app.log: |
      INFO  start
      ERROR db timeout
check:
  - desc: error.txt 가 존재한다
    cmd: test -f /work/error.txt
hints:
  - 특정 문자열이 든 줄만 뽑는 명령은 grep 이다.
solution: grep ERROR /work/app.log > /work/error.txt
```

`solution` 은 장식이 아니라 **테스트 픽스처**다.
자동 검증이 문제마다 `setup 적용 → 채점(실패해야 함) → solution 실행 → 채점(통과해야 함)`
순서로 돌린다. 그래서 문제가 조용히 망가지지 않는다.

## 9. 계정 전환 — 권한 문제가 진짜인 이유

권한 문제를 root 로 내면 의미가 없다. root 는 권한 검사를 우회하니
"실제로 막히는" 경험을 줄 수 없다.

그래서 문제마다 계정을 지정한다.

```yaml
setup:
  user: student
```

init 이 셸을 띄울 때마다 `/etc/dotslash/user` 를 다시 읽는다.
채점 채널이 그 파일을 고치고 셸을 종료시키면 다음 바퀴에서 새 계정으로 뜬다.
계정 전환 도구가 따로 필요 없다.

셸이 안 죽는 상황(`vi` 실행 중, `sudo -s` 로 중첩 셸)에서는
ttyS0 을 붙들고 있는 프로세스를 정리해서 강제로 넘긴다.

## 10. 디스크 — 마운트 문제가 진짜인 이유

부팅할 때 **빈 디스크를 하나 더 붙인다** (`/dev/sdb`, 64MB).
빈 버퍼라 다운로드가 0바이트다.

그래서 `fdisk` → `mkfs.ext4` → `mount` → `/etc/fstab` 이 전부 진짜로 동작한다.
`lsblk` 도 `findmnt` 도 실제 커널 상태를 보여준다.

v86 은 디스크 핫플러그가 안 돼서 부팅 때 미리 달아두고, 문제를 바꿀 때마다
앞 1MB 를 지워 초기화한다 (파티션 테이블과 파일시스템 시그니처가 거기 있다).

**안전장치**: 초기화 전에 대상이 루트 디스크인지 확인하고, 같으면 중단한다.
커널의 디스크 이름 부여가 확정적이지 않아서, 실수하면 루트를 날릴 수 있다.

## 11. 가상 네트워크 — ping·nmap 이 진짜인 이유

**흉내가 아니다.** 바깥으로 나가는 길은 없지만 게스트 커널은 진짜라서,
루프백에 주소를 여러 개 붙이면 그 사이의 ICMP·TCP 가 실제로 오간다.

```sh
netlab add 10.0.0.1 web01 22:SSH-2.0-OpenSSH_9.6 80
netlab add 10.0.0.2 db01 5432
```

- `ping web01` → 진짜 ICMP. RTT 도 실제 측정값이다
- `netstat -tln` → 진짜 리스닝 소켓
- `nmap -sT -p 22,80 web01` → 진짜 포트 스캔
- `nc web01 22` → 배너까지 읽힌다

**주소는 `/32` 로 붙인다.** `/24` 로 붙이면 서브넷 전체가 루프백으로 향해서
존재하지 않는 주소까지 ping 에 응답한다 — "죽은 호스트 찾기" 문제가 성립하지 않는다.

**nmap 은 `-sT`(connect 스캔)를 쓴다.** 기본 SYN 스캔은 raw 소켓이 필요한데
이 환경에서는 막혀 있다. 권한 없는 환경에서 `-sT` 를 쓰는 건 실무에서도 그대로 통하는 지식이다.

## 12. 파일트리

초보가 리눅스에서 제일 헤매는 건 명령어 문법이 아니라
**"내가 방금 뭘 바꿨는지 안 보인다"** 는 점이다.

명령을 칠 때마다 파일 목록을 다시 읽어 **바뀐 것만 색으로 표시**한다.

| 표시 | 뜻 |
|---|---|
| 초록 | 새로 생김 |
| 노랑 | 내용·크기·권한이 바뀜 |
| 빨강 취소선 | 삭제됨 |

`chmod` 를 치면 권한 숫자가 바뀌는 게 바로 보여서 `ls -l` 을 따로 안 쳐도 된다.
디스크 문제에서는 `lsblk` 요약도 같이 보여준다.

이것도 채점 채널로 조회하므로 당신 화면에는 명령이 안 보인다.

## 12-1. 홈 — 문제 고르기

문제가 72개다. 처음에는 문제 창 위의 드롭다운 하나에 전부 넣어뒀는데,
줄이 한 줄씩 쌓이니 지금 어느 레벨을 하고 있는지도 안 보였다.

지금은 **홈**이 따로 있다. **레벨 → 카테고리 → 문제** 세 단으로 나눠 놓고,
문제마다 본문 첫 줄을 요약으로 붙여서 열어보지 않고도 뭘 하는 문제인지 보이게 했다.
레벨 제목 옆의 `8/15` 는 그 레벨에서 몇 개를 통과했는지다.

문제 창에는 **같은 레벨 안에서 앞뒤로 가는 버튼만** 남겼다.
레벨을 건너뛰는 이동은 홈에서 한다 — 문제를 푸는 중에 필요한 이동은
"이 레벨의 다음 문제" 하나뿐이고, 나머지 선택지는 방해가 되기 때문이다.

홈은 별도 페이지가 아니라 터미널 위에 덮는 화면이다.
페이지를 나눴으면 홈에 갈 때마다 VM 을 다시 띄워야 한다.

### 기본명령어 탭

**이 환경에는 `man` 이 없다.** 매뉴얼 페이지를 넣으면 방문자가 받는 용량이 그만큼
늘어나서 뺐다. 그런데 수집 기록에 `man grep` 을 치고 그대로 나간 흔적이 남아 있었다 —
막혔을 때 볼 곳이 없었던 것이다. 그 자리를 메우는 탭이다.

명령어마다 한 줄 설명·사용법·자주 쓰는 옵션·예시를 적어뒀고, 이름뿐 아니라
설명과 옵션까지 검색된다 ("정렬" 로 `sort` 가 나온다).

**여기 적은 예시는 전부 게스트에서 실제로 실행해본 것이다** (`spike/lint-commands.mjs`).
이 게스트는 일반 리눅스와 다르다 — GNU 와 busybox 가 섞여 있어 `ps aux` 가 안 된다.
인터넷 치트시트를 베껴 넣으면 사이트가 자기 VM 에 대해 거짓말을 하게 되므로,
검증을 통과하지 못한 예시는 싣지 않는다.

**터미널에 치는 셸은 bash 다.** 배우는 사람이 보는 자료가 거의 bash 기준이고,
실제 서버에서도 로그인해서 쓰는 셸은 대개 bash 다. 배열, `{1..5}`, `${v^^}`,
`<<<`, `<(...)` 가 그대로 된다.

다만 **스크립트는 로그인 셸이 아니라 첫 줄의 `#!` 를 따라간다.** `#!/bin/sh` 로 적으면
busybox sh 로 도는 것이라 위 문법이 그 안에서는 안 된다. 그래서 스크립트 문제는
`#!/bin/bash` 를 안내한다. 실무 서버의 `/bin/sh` 도 대개 dash·ash 라 같은 구분이 그대로 있다.

맨 끝에 **안 되는 것**을 근거와 함께 모아뒀다. 32비트라서 없는 것(systemd),
용량 때문에 뺀 것(`man`, `curl`), 셸이 달라서 안 되는 것(배열, `<<<`)은 이유가
서로 다르므로 하나로 뭉뚱그리지 않는다.

**"안 된다"도 검증한다.** 항목마다 그것을 실제로 시도해보는 명령을 달아두고,
전부 실패해야 통과시킨다. 이 장치가 없을 때 틀린 항목을 실었다 —
`grep -P` 를 "빌드에서 빠졌다"고 적었는데 실제로는 된다 (GNU grep 3.12).
busybox 가 grep 을 대던 시절의 메모가 그대로 남아 있었던 것이다.

## 13. 진도 저장

브라우저의 `localStorage` 에만 저장한다. 계정이 없다.

- 푼 문제 목록과 마지막으로 보던 문제
- 화면 설정 (글자 크기, 색, 테마)
- **풀이 기록** — 그 문제를 풀 때 실제로 친 명령들

합쳐서 몇 KB 다. 다시 들어오면 홈의 `이어서` 로 마지막 자리로 돌아간다.
"진도 초기화" 로 지울 수 있다.

푼 문제를 다시 열면 `지난 풀이 보기` 가 생긴다. 정답과는 다른 물건이다 —
**내가 실제로 한 삽질이 그대로 남아 있어서**, 다시 풀 때 어디서 막혔는지가 보인다.

기록은 키 입력이 아니라 **터미널 화면에 그려진 줄**에서 뽑는다. 방향키로 이전 명령을
불러오거나 탭 완성을 쓰면 누른 키와 실제 명령이 달라지는데, 화면에는 편집이 끝난
최종 결과가 이미 들어 있기 때문이다. 덤으로 vi 편집 중에 친 것은 자동으로 걸러진다.

기기 간 동기화는 안 된다. 그건 계정이 필요한 일이라 미뤄뒀다.

## 13-1. 무엇이 수집되는가

문제를 **떠날 때** 한 건이 서버로 간다. 어느 문제에서 사람들이 막히는지 알아내
문제를 고치는 데만 쓴다.

| 담기는 것 | |
|---|---|
| 문제 번호 | |
| 결말 | 통과 / 못 푼 채 이동 / 탭 닫음 |
| 친 명령 목록 | |
| 걸린 시간, 힌트를 몇 개 봤는지, 정답을 봤는지 | |
| 목표를 몇 개까지 달성했는지 | 3개 중 2개와 0개는 의미가 정반대다 |

**신원은 아무것도 담기지 않는다.** 계정도, IP도, 기기를 알아볼 수 있는 것도 없다.
알고 싶은 것은 "사람들이 어떻게 푸는가"이지 "누가 풀었는가"가 아니다.
담을 게 없으면 유출될 것도 없다.

설정에서 끌 수 있다. 통과한 것만 모으면 성공률의 분모가 없어서 실패도 같이 모으지만,
**화면에는 아무것도 표시하지 않는다** — "틀렸다"고 알리면 정답 보기를 피하게 되고,
그러면 막혔다는 신호 자체가 사라지기 때문이다.

문제 화면 위쪽의 `N명이 도전 · X% 성공` 이 그렇게 모인 결과다.
표본이 5명 미만인 문제는 아예 표시하지 않는다 — 1명이 실패하면 0%, 1명이 풀면 100%인
숫자는 정보가 아니라 소음이다.

## 14. 성능

| | |
|---|---|
| 첫 방문 | 약 2초 + 다운로드 시간 (26.8MB) |
| 재방문 | 약 2초 (다운로드는 캐시된다) |
| 탭당 메모리 | 약 256MB (게스트 RAM 128 + 루트 디스크 64 + 스크래치 64) |

스냅샷 복원으로 바꾸면서 **기기 성능을 거의 타지 않게 됐다.**
부팅하던 시절에는 4배 느린 CPU 에서 45초까지 늘어났다 (4번 항목의 표 참고).

그래도 **연습 중 명령을 실행하는 속도는 여전히 CPU 를 탄다.**
v86 은 순수 CPU 에뮬레이션이라 다른 프로그램이 CPU 를 많이 쓰면 그만큼 느려진다.

브라우저 차이는 거의 없다 (Chrome 과 Safari 를 같은 조건에서 재보니 3% 이내).

**안 보이는 탭은 VM 을 멈춘다.** 탭마다 게스트가 계속 돌면
지금 보고 있는 탭까지 느려지기 때문이다. 돌아오면 멈춘 자리에서 이어진다.

새로고침을 반복해도 느려지지 않는다. 페이지를 새로 열면 VM 이 통째로 해제되고
다시 만들어져서 쌓이는 상태가 없다.

## 15. 안전한가

**당신 브라우저 안에서만 돈다.** 서버에는 아무것도 없다.

- 게스트에서 root 를 따든 커널을 부수든 **자기 탭 하나 망가지는 게 전부**다.
  새로고침하면 원래대로다
- **네트워크 인터페이스 자체가 없다.** 막아둔 게 아니라 장치가 존재하지 않는다.
  게스트 안에서 무슨 파일을 고쳐도 없는 하드웨어는 생기지 않는다
- WebAssembly + 브라우저 샌드박스 안이라 호스트 파일이나 소켓에 접근할 수 없다
- 사용자끼리 서로 격리된다. 공유되는 상태가 없다

공개 전에 게스트 안에서 직접 두드려 확인한 값이다. 설정을 읽고 내린 결론이 아니다.

| 시도 | 결과 |
|---|---|
| `wget http://1.1.1.1/` | Network unreachable |
| `ping 8.8.8.8` | sendto: Network unreachable |
| `nmap 192.168.1.1` | failed to determine route |
| `nslookup google.com` | no servers could be reached |
| `ls /sys/class/net` | `lo` 하나뿐 |

`ping`·`nmap` 문제가 진짜로 도는 것은 루프백에 `/32` 주소를 붙여서다.
그 패킷은 게스트 커널 밖으로 나가지 않는다 (11 참고).

입력한 명령은 문제를 마칠 때 **문제 개선용으로만** 수집된다 (13-1 참고).
신원과 연결되는 정보는 함께 보내지 않고, 설정에서 끌 수 있다.
어느 쪽이든 **명령이 실행되는 곳은 당신의 브라우저**이지 서버가 아니다.

## 16. 한계 — 지금 못 하는 것

정직하게 적어둔다.

- **32비트 전용.** v86 이 64비트 커널을 지원하지 않는다
- **systemd 없다.** `systemctl`, `journalctl` 은 못 쓴다. 서비스 관리 실습은
  서버 사이드 VM 이 필요해서 미뤄뒀다
- **외부 네트워크 없다.** `curl https://...`, `apt install`, `git clone` 은 안 된다
- **속도.** 컴파일이나 큰 파일 처리는 느리다
- **모바일.** 로드는 되지만 메모리와 CPU 부담이 크다

## 17. 어떻게 검증하는가

문제와 채점기가 조용히 망가지지 않도록 3단으로 검사한다.

| 단계 | 시간 | 무엇을 |
|---|---|---|
| 정적 린트 | 즉시 | 문제 파일의 흔한 실수 |
| 문제 검증 | 4분 | 전 문제를 실제로 풀어봄 (브라우저 없이) |
| 브라우저 검증 | 5분 | UI 배선까지 포함해 71항목 |
| **배포본 검증** | 5분 | **실제로 올리는 파일**을 그대로 띄워서 71항목 |

마지막 단계가 따로 있는 이유는, 빌드가 파일 이름을 갈고 주석을 떼고 코드를 압축하기
때문이다. 소스는 멀쩡한데 배포본만 깨질 수 있고, 그건 소스를 검사해서는 안 잡힌다.

린트가 잡는 것들:
- **채점 조건이 상태를 바꾸는 경우** — 다음 판정이 오염된다
- **부정 조건인데 대상이 없을 때도 통과하는 경우** — 공허한 참
- 계정과 파일 소유자가 어긋나는 경우

문제 검증은 각 문제에 대해 **정답을 실제로 입력해보고**,
같은 상태에서 여러 번 채점해 결과가 흔들리지 않는지도 본다.

## 18. 기술 스택

| | |
|---|---|
| 에뮬레이터 | v86 (BSD-2) |
| 게스트 OS | Alpine Linux 3.23.5 (x86) |
| 커널 | Linux 6.18.36 LTS |
| 터미널 UI | xterm.js |
| 문제 정의 | YAML (js-yaml) |
| 빌드 | Node.js 스크립트 (번들 없음, esbuild 로 주석 제거·압축만) |
| 배포 | Cloudflare Pages (정적) |
| 수집 | Cloudflare Worker + D1 |

프레임워크를 쓰지 않았다. 브라우저가 받는 앱 코드는 전부 합쳐 40KB 남짓이다.

**캐시 때문에 배포가 반쯤 적용되는 일**이 한 번 있었다. CDN 이 `.js` 에 4시간
캐시를 씌워서, 새 `index.html` 과 옛 `main.js` 가 섞여 앱이 통째로 안 떴다.
지금은 빌드가 파일 이름에 내용 해시를 붙인다 (`main.js?v=...`). `index.html` 은
캐시되지 않으므로 항상 새 이름을 가리키고, 그 이름은 캐시에 있을 수가 없다.
스냅샷에도 같은 해시가 붙어서 "앱은 새건데 게스트는 옛것" 도 생기지 않는다.

## 19. 왜 이렇게 만들었나

리눅스 명령어 연습 사이트는 이미 있다. 대부분 **서버에서 컨테이너나 VM 을 띄운다.**
그러면 사용자가 늘수록 비용이 사용자 수에 비례해 늘고, 개인이 오래 운영하기 어렵다.

브라우저에서 돌리면 **사용자가 몇 명이든 서버 비용이 고정**이다.
정적 파일만 서빙하면 되기 때문이다.

대신 32비트 제약과 속도를 감수해야 했다. 파일·텍스트·권한·디스크·네트워크까지는
이 방식으로 충분히 커버된다고 판단했다.
